# ssh-key-creation Specification

## Purpose
Let the user create SSH key items with a key Prizm generates or imports, and keep every SSH key's
fingerprint computed from its public key, so all Bitwarden clients and servers see a complete,
consistent key.

## Requirements

### Requirement: New SSH key items are created with a generated key
When the user creates an SSH key item, the system SHALL fill it with a freshly generated Ed25519 key pair and SHALL send the private key, the public key and the fingerprint together in the create request.

#### Scenario: Create an SSH key on Vaultwarden
- **GIVEN** the user is signed in to Vaultwarden 1.37.4
- **WHEN** the user chooses New Item → SSH Key, enters a name and saves
- **THEN** the create request SHALL contain `privateKey`, `publicKey` and `keyFingerprint`, each encrypted
- **AND** after the next sync the web vault SHALL show the same three values

#### Scenario: Generate a different key
- **GIVEN** the create sheet shows a generated key
- **WHEN** the user chooses "Generate new key"
- **THEN** all three fields SHALL change together

### Requirement: The fingerprint is computed from the public key
The fingerprint SHALL be `SHA256:` followed by the base64 encoding, without padding, of the SHA-256 hash of the public key blob, the form printed by `ssh-keygen -l`.

#### Scenario: Known answer
- **GIVEN** a public key generated by OpenSSH
- **WHEN** the system computes its fingerprint
- **THEN** the result SHALL equal the output of `ssh-keygen -l` for that key

### Requirement: An unencrypted OpenSSH Ed25519 key can be imported
The system SHALL let the user import an unencrypted OpenSSH Ed25519 private key from the clipboard or from a file. It SHALL fill the private key, the public key and the fingerprint from it.

#### Scenario: Import from the clipboard
- **GIVEN** the clipboard holds a valid unencrypted OpenSSH Ed25519 private key
- **WHEN** the user chooses "Import key…" → "From clipboard"
- **THEN** the three fields SHALL show that key's private key, its public key and its fingerprint

#### Scenario: Import from a file
- **GIVEN** a file holding a valid unencrypted OpenSSH Ed25519 private key
- **WHEN** the user chooses "Import key…" → "From file…" and picks it
- **THEN** the three fields SHALL show that key's values
- **AND** a file larger than 16 KiB SHALL be refused without being read whole

#### Scenario: Stored private key loads in OpenSSH
- **GIVEN** a key that was generated, or imported from text with CRLF line endings
- **WHEN** the stored private key text is given to `ssh-keygen -y`
- **THEN** OpenSSH SHALL print the stored public key

### Requirement: Imports are checked and refused when they cannot be checked
The system SHALL refuse an import, SHALL keep the current key, and SHALL show a specific message when the input is damaged, passphrase-protected, of an unsupported format or key type, or inconsistent. It SHALL NOT log any key text.

#### Scenario: Passphrase-protected key
- **GIVEN** the input is an OpenSSH private key protected by a passphrase
- **WHEN** the user imports it
- **THEN** the system SHALL refuse it
- **AND** the message SHALL tell the user to remove the passphrase and import again

#### Scenario: Public key does not belong to the private key
- **GIVEN** an OpenSSH Ed25519 key whose public key differs from the one derived from its private key
- **WHEN** the user imports it
- **THEN** the system SHALL refuse it as inconsistent

#### Scenario: Refused import keeps the current key
- **GIVEN** the create sheet shows a key
- **WHEN** an import is refused
- **THEN** the three fields SHALL keep their values and the message SHALL be shown and announced

#### Scenario: Security key
- **GIVEN** an OpenSSH key of type `sk-ssh-ed25519@openssh.com`
- **WHEN** the user imports it
- **THEN** the system SHALL refuse it with a message that security keys can't be stored in a vault

#### Scenario: Truncated input
- **GIVEN** an OpenSSH key cut off at any field boundary
- **WHEN** the user imports it
- **THEN** the system SHALL refuse it as damaged and SHALL NOT crash

#### Scenario: Unsupported type or format
- **GIVEN** an RSA key, an ECDSA key, a PEM, PKCS#8 or PuTTY key
- **WHEN** the user imports it
- **THEN** the system SHALL refuse it and name the unsupported type or format

### Requirement: A missing fingerprint is filled in on save
When the user saves an SSH key item that has a public key and no fingerprint, the system SHALL compute the fingerprint from the public key and send it. It SHALL NOT replace an existing fingerprint.

#### Scenario: Item created by an older Prizm version on the official server
- **GIVEN** an SSH key item with a public key and no fingerprint
- **WHEN** the user changes its name and saves
- **THEN** the update request SHALL contain the computed fingerprint

#### Scenario: Public key that cannot be read
- **GIVEN** an SSH key item with no fingerprint and a public key that is not `<type> <base64>`
- **WHEN** the user saves it
- **THEN** the update request SHALL contain no fingerprint

#### Scenario: Existing fingerprint
- **GIVEN** an SSH key item with a fingerprint
- **WHEN** the user saves it
- **THEN** the update request SHALL contain that fingerprint unchanged
