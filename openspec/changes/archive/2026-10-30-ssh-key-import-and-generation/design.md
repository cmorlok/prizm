# Design

## Context

Facts about servers and official clients are in `fix-ssh-key-roundtrip`, design Context. Summary:
no server derives or generates SSH key data; Vaultwarden hides any SSH item whose fingerprint,
private key or public key is empty; official clients generate an Ed25519 key or import one, and fill
all three fields together. Format of the stored values, as the official SDK writes them:
- private key: unencrypted OpenSSH (`-----BEGIN OPENSSH PRIVATE KEY-----`, `openssh-key-v1`)
- public key: OpenSSH `authorized_keys` text, `ssh-ed25519 <base64 blob>`
- fingerprint: `SHA256:` + unpadded base64 of SHA-256 over the public key blob

Prizm today (after `fix-cipher-edit-data-loss` and `fix-ssh-key-roundtrip`): `toRawSSHKey` sends the
stored fingerprint back on an edit and none on a create, and Prizm has no key code at all. The key
fields are read-only, an SSH item without private or public key has the edit block
`incompleteSSHKey`, and `ItemType.isCreatable` keeps SSH Key out of New Item, with
`VaultBrowserViewModel.createItemType` refusing it as a backstop.

## Goals / Non-Goals

**Goals**
- Every SSH key Prizm creates has private key, public key and fingerprint that agree with each other.
- Prizm only stores an imported key after checking everything it can check without new crypto.
- No new dependency and no hand-rolled cryptographic algorithm.

**Non-Goals:** see proposal.md.

## Decisions

### D1. Build it natively; do not use the Bitwarden SDK (decided 2026-10-29)

Recorded so it is not reopened. Checked 2026-10-29:
- `bitwarden/sdk-swift` `Package.swift` on `main` declares `platforms: [.iOS(.v13)]` only, with one
  binary target (`BitwardenFFI`) from a blob-storage URL. It is the release channel for
  `sdk-internal`'s `bitwarden-uniffi` bindings.
- `sdk-internal`'s README says it is for Bitwarden's own apps, "not intended for public use or
  supported at this stage", with an interface that "may change without warning".
- `sdk-internal` is licensed "GPL v3.0 OR BITWARDEN SOFTWARE DEVELOPMENT KIT LICENSE" (per its
  `LICENSE`; the SDK License text was not read). Prizm is MIT, so taking the GPL option would make the
  distributed app GPL-3.
- `sdk-sm` is the separate Secrets Manager SDK and is not relevant.
- Constitution §III prohibits third-party crypto libraries except Argon2Swift without an amendment,
  and "Bitwarden SDK / sdk-swift" is listed as evaluated and rejected. Revisit only if Bitwarden
  officially ships a macOS slice.

What Apple's frameworks cover: Ed25519 generation (`Curve25519.Signing`), SHA-256 (CryptoKit), base64
and length-prefixed parsing (Foundation). What they do not cover (passphrase-protected keys,
PKCS#8) is out of scope.

The SDK source stays a *reference to read*, as for every other change. No code and no test fixtures
are copied from it (D8).

### D2. Layering

- **Domain** (Foundation only): `protocol SSHKeyService` with
  `generate() throws -> SSHKeyMaterial`, `parse(privateKeyText:) throws -> SSHKeyMaterial` and
  `fingerprint(forPublicKey:) -> String?`. `SSHKeyMaterial` holds the three strings and prints
  redacted. `enum SSHKeyError: Error, Equatable` has one case per refusal (D4).
- **Data**: `SSHKeyServiceImpl`, the only file that imports CryptoKit for this.

The Constitution (§III) says crypto is wrapped "behind a `PrizmCryptoService` protocol". That
protocol is an `actor` for vault crypto (`Data/Crypto/PrizmCryptoService.swift`); SSH key code has no
shared state and needs no actor. A separate protocol follows the rule's purpose (Data layer only,
Domain sees plain types) and is simpler than growing `PrizmCryptoService`. Noted for the PR text.

### D3. Generation and format

Ed25519 only, as in the official clients' default.
- Key: `Curve25519.Signing.PrivateKey()` (system CSPRNG).
- Container `openssh-key-v1`: magic `openssh-key-v1\0`, cipher `none`, kdf `none`, empty kdf options,
  one key, the public key blob, then the private section: two equal random 32-bit check integers,
  key type, 32-byte public key, 64-byte private key (seed then public key), comment, padding bytes
  `1, 2, 3, …` up to the 8-byte block size. Armoured with the BEGIN/END OPENSSH PRIVATE KEY lines,
  base64 wrapped at 70 columns, trailing newline.
- Public key text: `ssh-ed25519 ` + base64 of the blob (`string "ssh-ed25519"`, `string <32 bytes>`).
- Fingerprint: `"SHA256:" + base64(SHA-256(blob))` with `=` padding removed.
- Comment: empty (Open Question 3).

The generated private key is checked against OpenSSH: `ssh-keygen -y -f` must print the public key
text and `ssh-keygen -l -f` the fingerprint (task 2.4, not in the unit tests). Done 2026-10-30 with
OpenSSH 9.6p1 in the devcontainer, for three keys generated by a temporary test on the Mac: both
matched for all three. One of them, re-imported from CRLF text, was stored byte-identical to the
generated key and loads in `ssh-keygen`.

### D4. Import: accept little, check everything

Accepted: an unencrypted `openssh-key-v1` containing exactly one Ed25519 key. Input is normalised
first: `\r\n` and `\r` become `\n`, and surrounding whitespace is ignored.

Checks, each a typed error and each with a test, in this order:
0. Size at most 16 KiB. Text that starts with another armour (`-----BEGIN RSA PRIVATE KEY-----`,
   `BEGIN EC PRIVATE KEY`, `BEGIN PRIVATE KEY`, `BEGIN ENCRYPTED PRIVATE KEY`) or a PuTTY header
   (`PuTTY-User-Key-File-`) is `unsupportedFormat` naming PEM, PKCS#8 or PuTTY; anything else
   without the OpenSSH armour is `notOpenSSHKey`.
1. One BEGIN/END OPENSSH pair with valid base64 between them (`notOpenSSHKey`).
2. Magic `openssh-key-v1\0` (`unsupportedFormat` for another one; a decoded body that is a cut-off
   prefix of the magic is `damaged`), then the cipher, kdf and kdf options strings are read.
3. Number of keys is 1 (`unsupportedFormat`, "more than one key").
4. The outer public key blob is `ssh-ed25519` with exactly 32 key bytes and nothing after them.
   `sk-…` types (security keys such as a YubiKey) are `securityKey`; other types are
   `unsupportedKeyType`, named RSA, DSA or ECDSA (any other type is not named, so no input text is
   shown). This comes before the cipher check, so an encrypted RSA key is reported as
   an unsupported type, not as passphrase-protected.
5. Cipher `none` (`passphraseProtected` otherwise: "Remove the passphrase with `ssh-keygen -p` and
   import again"); kdf `none` and empty kdf options (`damaged` otherwise: an unencrypted key with a
   kdf is malformed).
6. Nothing follows the private section in the outer blob, and the section's length is a non-zero
   multiple of 8 (`damaged`).
7. The two check integers are equal (`damaged`).
8. The inner key type is the outer one, the inner public key equals the outer one, the private key is
   exactly 64 bytes, and its last 32 bytes equal the public key (`inconsistent`; a wrong length is
   `damaged`). Tools that sign with the 64-byte form use those bytes as the public key.
9. The public key derived from the 32-byte seed with CryptoKit equals all of them (`inconsistent`).
   This is the check that private and public key belong together; OpenSSH 9.6 does not make it.
10. The comment string is readable, and padding is exactly `1, 2, 3, …` with fewer than 8 bytes
    (`damaged`).

Every length field is read through a bounds-checked reader. A length that exceeds the remaining bytes
throws `damaged`; there is no force-unwrap or unchecked index on untrusted input. Tests cut a valid
key's decoded bytes at every byte and re-armour them: every non-empty cut is `damaged`, and none
crashes.

**Stored text:** after the checks pass, Prizm stores a new armour of the checked bytes (BEGIN line,
base64 at 70 columns, END line, `\n`), not the pasted text. This is not a re-serialisation: the
bytes, and with them the comment, are unchanged. It makes sure other clients and `ssh-keygen` can
load what Prizm accepted, even when the input had CRLF line endings or one long base64 line, which
`ssh-keygen` 9.6 refuses (spec challenge, 2026-10-30).

**Public key text:** `ssh-ed25519 <base64>` without a comment, also for imported keys that have one;
the comment stays in the private key. Fingerprints are compared by their `SHA256:` token only.

**File import:** the file is read through its security-scoped URL, at most 16 KiB + 1 bytes are read
(a larger file is `notOpenSSHKey` without reading it whole), and input that is not UTF-8 is
`notOpenSSHKey`. "From clipboard" reads a string; when the pasteboard holds a file URL instead (a key
file copied in Finder), that file is imported the same way.

**Rejected alternative:** accept any key and compute only the fingerprint from the outer public key.
It would store a pair that may not match (check 9 is the point of this change).

### D5. Fingerprints on create and on save

- **Create:** `toRawSSHKey` computes the fingerprint from the draft's public key and encrypts it with
  the item's other fields. A draft fingerprint that differs from the computed one is a programming
  error and fails the save (`CipherMapperError`), so a mismatched pair is never sent.
- **Edit:** the stored fingerprint goes back as received (`fix-ssh-key-roundtrip` D1). When it is
  missing, or decrypts to an empty or blank string (items created by older Prizm versions on the
  official server), the computed one is sent instead. An existing fingerprint is never replaced, even
  when it differs from the computed one (Open Question 2). If the public key text does not parse as
  `<type> <base64>`, nothing is sent for it.
- The mapper calls `SSHKeyServiceImpl.fingerprint(forPublicKey:)`, a static function of the Data
  layer, so `CipherMapper` needs no new dependency.
- Items Vaultwarden hides are unaffected: they stay uneditable (`fix-ssh-key-roundtrip` D3).

### D6. Create sheet

New Item → SSH Key opens the create sheet with a key already generated, as the web vault does. It
shows the three fields read-only (the rows `fix-ssh-key-roundtrip` D2 defines for editing) and two
actions: "Generate new key" and "Import key…". Import offers "From clipboard" and "From file…"
(`fileImporter`, already permitted by the entitlement). A refused import shows its message inline and
leaves the current key unchanged. Save sends private key, public key and fingerprint together,
encrypted with the same key rule as every other create (today `fix-org-key-required-on-write`;
later `per-item-key-on-create`, not landed yet). The `isCreatable` filter from `fix-ssh-key-roundtrip` is deleted, not
kept as dead code.

`DraftSSHKeyContent` keeps its three key fields read-only for the edit form and gains one atomic
`mutating func replace(with: SSHKeyMaterial)`, used only by the create sheet; `ItemEditViewModel`
gets the `SSHKeyService` injected for generate and import. The key generated when the sheet opens is
part of the starting state, so discarding an untouched sheet asks nothing.

VoiceOver: each row keeps its label and the copy hint of the detail rows, as in
`fix-ssh-key-roundtrip` D2; the actions are labelled; an import error is announced when it appears
(§VIII). Typography and spacing tokens only.

On create, `toRawSSHKey` encrypts the draft's three values; there is no stored record. The
`createItemType` backstop goes with the filter.

### D7. Secrets, logs, pasteboard

- Key text is never logged: `SSHKeyMaterial` has a redacted description and `SSHKeyError` carries no
  key text. Once the values are in `DraftSSHKeyContent`, its default description would print them,
  like every other draft field; no code logs drafts, which is the existing rule.
- The pasteboard is read only when the user chooses "From clipboard". Prizm does not clear the user's
  clipboard after an import: the content is theirs.
- Copying the private key from the sheet uses the existing concealed-copy path
  (`clipboard-hardening`).
- Memory: best effort and no worse than other key material (`harden-key-lifecycle-and-logging`). The
  byte buffers that hold the seed or the decoded key are zeroed; Swift `String` cannot be, and copies
  made by Foundation may remain, which is the same limit the rest of the app has.

### D8. Test vectors

Known-answer vectors are produced with the local OpenSSH tools, not taken from the SDK's tests,
which are GPL-3.0 / SDK-licensed material in an MIT repository. For each vector the fixtures README
records the exact `ssh-keygen` command, the OpenSSH version, and the output of `ssh-keygen -y` and
`-l`. Negative vectors (truncated, wrong check integer, mismatched public key, passphrase-protected,
RSA, ECDSA, PEM, PKCS#8) are made the same way and by editing bytes.

## Risks / Trade-offs

- **[Medium] Parsing untrusted input** (the clipboard can hold anything). → D4: size cap,
  bounds-checked reader, truncation tests, one typed error per refusal, mandatory security review.
- **[Medium] Users with RSA or passphrase-protected keys cannot import.** → Specific messages tell
  them what to do; RSA/ECDSA are Open Question 1.
- **[Low] Prizm and OpenSSH disagree on a format detail.** → D3 task 2.4 checks generated keys with
  `ssh-keygen`; D8 vectors come from it.
- **[Low] An existing wrong fingerprint stays.** → Open Question 2.
- **[Low] The two SSH changes ship far apart,** leaving users without creation for a while. → Ship
  them close together (proposal Dependencies).

## Review

Independent review on 2026-10-30, by a fresh reviewer who read the branch only. No blockers. The
reviewer re-checked the three accepted vectors with Python. Findings and what was done (review
fixes test-first: red `20261030T132803Z`, green `20261030T133013Z`):
- Fixed: the refusals for an unsupported type or format did not name what was found, which the
  spec requires. `SSHKeyError.unsupportedKeyType` and `.unsupportedFormat` now carry the name
  (RSA, DSA, ECDSA; PEM, PKCS#8, PuTTY, more than one key). An unknown type is not named, so no
  input text is shown.
- Fixed: the truncation test accepted any error for cuts longer than 14 bytes. It now expects
  `damaged` for every non-empty cut, as the code already did, and D4 says so.
- Fixed: nothing stopped an SSH create without a fingerprint below the view model. Now
  `VaultRepositoryImpl.create` refuses a type 5 draft without all three values
  (`sshKeyIncomplete`) before anything is sent. The check is in the repository, not the mapper,
  because tests use the mapper's create path to build fixtures with fake keys.
- Fixed: the comment and D7 claimed that every buffer holding the seed or the decoded key is
  zeroed. Both now say "best effort": the arrays this code owns are zeroed, but Foundation
  temporaries, CryptoKit's own copy and Swift strings are not. Capacity is not reserved up front.
- Fixed: the protocol doc said the private key is kept "as supplied", and D4 mentioned
  "surrounding text". The doc now describes the new armour, and D4 makes no claim about text
  around the key.
- Fixed: a refusal was announced only when its text changed, so the same bad key imported twice
  was announced once. The sheet now announces on a refusal counter.
- Fixed: a file-read error was logged with a public `localizedDescription`, which can contain the
  file path. It now uses `ErrorLog.describe`.
- Declined: `Spacing.headerGap` (8 pt) is reused as the spacing between the two key buttons. The
  value fits, and a new token for a single use was not added (§VI).
- Partly open: accessibility (task 4.4). The rows, buttons and announcement exist, but the UI test
  finds only the rows and "Generate new key" by label; copy hints and the announcement are not
  checked. That waits for the pending UI run and Christian's decision (open.md).

**Security (task 5.4).** `SSHKeyServiceImpl` is the only new code that touches key material. It
imports CryptoKit and Foundation only and lives in the Data layer; the Domain sees strings
(`SSHKeyMaterial`) and a typed `SSHKeyError`. It adds no dependency and no algorithm of its own:
Ed25519 and SHA-256 come from CryptoKit, and the code only reads and writes length-prefixed fields.

Clipboard and file input are untrusted:
- Input over 16 KiB is refused unread, and a file is read to at most 16 KiB + 1 bytes.
- Every length is checked against the bytes that remain, and a length that runs past the end
  throws `damaged`. No force-unwrap or unchecked index touches the input; a test cuts a valid key
  at every byte.
- The checks run in the order of D4. The last one derives the public key from the seed, so a
  private and public key that do not belong together are refused. OpenSSH 9.6 does not make this
  check.
- Prizm stores a new armour of the checked bytes, not the pasted text.

On write:
- A create computes the fingerprint from the public key and refuses a draft value that differs.
  The repository refuses a create without all three values.
- An edit sends a stored fingerprint back as received, and fills in only a missing or blank one.
- Hidden or incomplete keys stay blocked (`fix-ssh-key-roundtrip`).

Secrets:
- No key text reaches a log or an error: `SSHKeyMaterial` prints redacted, errors carry only
  type names, and the only new log lines name an error type or the refusal.
- The pasteboard is read only on "From clipboard" and is not cleared. Copies go through the app's
  concealed, auto-clearing clipboard service.
- Zeroing is best effort, as described above.

Archive pass and hand check (2026-10-30):
- Fixed: a failure of the file picker was dropped silently (Constitution §V); it is now logged,
  shown and announced like a refusal.
- Fixed: a refused import was shown but not spoken; the closing Import menu cut off the
  default-priority announcement. It is now posted at high priority through AppKit, as the edit sheet
  does. Confirmed by Christian with VoiceOver.
- Open Question 1 decided by Christian: no RSA/ECDSA import for now.

## Open Questions

1. **RSA and ECDSA unencrypted import as a second stage?** ECDSA P-256/384/521 can be fully checked
   with CryptoKit (derive the public key from the private scalar). RSA can only be checked for
   consistency between the outer and inner public key blobs, because checking the pair needs RSA math
   that Prizm will not hand-roll. Decide at the end of stage 1, from how many users hit the refusal.
   Decided 2026-10-30 by Christian: no follow-up for now; revisit when users ask.
2. Should a stored fingerprint that does not match the public key be shown as a warning? Prizm can
   now compute it. Default: no, until a user asks (`fix-ssh-key-roundtrip` Open Question 2).
3. Empty comment in generated keys, or `user@host`? Default, used: empty.
