# Test fixtures captured from Vaultwarden 1.37.4

**Security review: this directory is part of the security review (committed test credentials).**

Everything in here, except `cipher-kitchen-sink.json` (synthetic, see the table), comes from a
throwaway account on a local Vaultwarden test server. All data in it is fake, and the master
password below is deliberately public.

## Files

| File | What it is |
|---|---|
| `sync-golden-1.37.4.json` | Scrubbed `GET /api/sync?excludeDomains=true` from Vaultwarden 1.37.4: six ciphers, no folders, one organization with its collections, the profile with its protected keys |
| `stale-put-400-1.37.4.json` | The exact HTTP 400 body of an update whose `lastKnownRevisionDate` is older than the stored one (design.md "Server behavior", E5) |
| `cipher-kitchen-sink.json` | Synthetic, hand-written, not captured from a server: six ciphers covering every nested level, unknown and null extras (int, double, a large integer, null), response-only keys at every rebuilt level, and wrong-typed new fields. Fake EncStrings only |

## The throwaway account

| Item | Value |
|---|---|
| Email | `prizm-fixture@example.com` |
| Master password | `prizm-fixture-not-a-secret` |
| KDF | PBKDF2-SHA256, 600000 iterations |

These values are public on purpose. Tests have to derive the master key to decrypt the fixture, and
the email is the PBKDF2 salt, so neither can be scrubbed. The account exists only on a Vaultwarden
server that was never reachable from the internet. Its address is not in the fixtures (see "What the
scrub changed").
Every item is fake: `example.com` URIs, a passkey registered at a webauthn.io test page, an SSH key
generated by Bitwarden for this purpose, and a small text attachment. Do not reuse this password for
anything.

## Where the data comes from

- **Authored on Vaultwarden 1.37.3** (`vaultwarden/server:1.37.3@sha256:1587c45feaa479f1f5e8af3b00eded36bff77bcf1880cf8dbf0541706dd470e0`,
  `GET /api/version` 1.37.3, `/api/config` version 2026.6.0, gitHash `eb212e23`) on 2026-10-26.
  - The unkeyed control and twin logins were created in the web vault v2026.7.0 bundled with that
    server, with the `cipher-key-encryption` flag off, and no client saved them afterwards.
  - The other items were created with the Bitwarden browser extension 2026.10.0 (read on
    `chrome://extensions` before and after authoring) in Chrome (version not reported). The
    extension was the unpacked release build from the `bitwarden/clients` GitHub releases
    (`browser-v2026.10.0`), which Chrome does not update automatically, so the version stayed the
    same throughout. That extension pins Bitwarden SDK build 1075, which gives an item its own key only when the server
    sends the `cipher-key-encryption` flag. Vaultwarden does not send it, so the flag was added to the
    server's `/api/config` answer while the items were created.
  - Clients on SDK build 1087 (2026-10-05) or later give every item its own key without the flag
    (source-reviewed, not tested).
- **Migrated to and captured on Vaultwarden 1.37.4**
  (`vaultwarden/server:1.37.4@sha256:efb3cde962015fcc036b2ea625242248611943b27212ebf4392841fb30fad055`,
  `GET /api/version` 1.37.4, `/api/config` version 2026.6.0, gitHash `7c188967`) on 2026-10-26, by
  restoring the 1.37.3 data directory into the 1.37.4 server. Both image digests are the ones the
  capture used; the server reports its version and gitHash, but the running image's digest was not
  read back from the container.
- **Prizm** as it was before this change was used for the E0 and E1 checks in design.md "Server
  behavior".

## What the scrub changed

The raw capture is not part of this change. The scrubbed file differs from it only here:

- every UUID is replaced by a fixed dummy of the form `00000000-0000-4000-8000-<12 digits>`, applied
  to the whole document, so relations (folder, organization, collection, attachment urls) still
  match;
- the attachment id is `a0000000000000000001`, its download token is `SCRUBBED` and its download
  url points at `https://vault.example.com`, not at the address of the capture server;
- `profile.name` is `Prizm Fixture`, `profile.securityStamp` is a fixed placeholder;
- the organization name in `profile.organizations` and `profile.organizationsNew` is
  `Prizm Fixture Org`.

Kept byte for byte: every EncString (names, notes, fields, per-item `key` values, `uriChecksum`,
passkey and password history ciphertext), the protected user key, private key and organization key,
every timestamp, and the email.

The scrub and its fail-closed checks (no JWT, no token, no IP address, no UUID left, ciphertext and
timestamps identical, master password, master key and server hash absent) were run with local
tooling that is not part of this change.

## Loading the fixtures in tests

Xcode copies the files flat into the test bundle's resources, with no subdirectory
(`PrizmTests.xctest/Contents/Resources/`, observed in a build of the test target). Load them by
file name with `Bundle(for:)` on a test-target class. Do not use `#filePath`: the test host is
sandboxed and cannot read the source tree.
